# Задание №6

## Проект

**Recipe from Fridge**

## Краткое описание проекта

**Recipe from Fridge** — это B2C-приложение, которое помогает пользователю подобрать рецепты по продуктам, которые уже есть дома.

Пользователь добавляет продукты из холодильника, а приложение предлагает подходящие рецепты, показывает недостающие ингредиенты и помогает меньше выбрасывать еду.

---

# 1. Цель анализа рисков

Цель анализа рисков — заранее определить возможные проблемы, которые могут повлиять на сроки, качество MVP, бюджет или пользовательскую ценность продукта.

Для проекта **Recipe from Fridge** были выделены 6 ключевых рисков:

1. Низкое качество подбора рецептов.
2. Недостаточная база рецептов.
3. Сложность ввода продуктов пользователем.
4. Scope creep — разрастание функциональности.
5. Проблемы с хранением пользовательских данных.
6. Низкий интерес пользователей после запуска MVP.

# 4. Подробное описание рисков

## Риск 1. Низкое качество подбора рецептов

### Описание

Главная ценность приложения — подбор рецептов по продуктам, которые уже есть дома. Если алгоритм будет предлагать неподходящие рецепты, пользователь быстро потеряет доверие к приложению.

### Тип риска

**Внутренний технический риск**

Этот риск связан с логикой работы самого продукта.

### Причины возникновения

- Неправильно настроен алгоритм совпадения ингредиентов.
- Система не учитывает синонимы продуктов.
- Пользователь вводит продукты в разных формах: “яйцо”, “яйца”, “куриные яйца”.
- Рецепты плохо размечены по ингредиентам.

### Вероятность

**Средняя**

На этапе MVP алгоритм может быть простым, поэтому ошибки в подборе вероятны.

### Влияние

**Высокое**

Если подбор рецептов работает плохо, продукт не выполняет главную задачу.

### Уровень риска

**Высокий**

### Стратегия реагирования

**Смягчить / предотвратить**

### План реагирования

- Начать с ограниченного набора популярных продуктов.
- Использовать словарь синонимов продуктов.
- Сортировать рецепты по проценту совпадения ингредиентов.
- Показывать пользователю недостающие ингредиенты.
- Протестировать алгоритм на 20–30 типовых наборах продуктов.
- Собрать обратную связь от первых пользователей.

### Индикатор риска

Пользователи часто открывают список рецептов, но не переходят в карточку рецепта.

---

## Риск 2. Недостаточная база рецептов

### Описание

Если в приложении будет мало рецептов, пользователь часто будет видеть пустой результат или однообразные варианты блюд.

### Тип риска

**Внутренний продуктовый риск**

Риск связан с наполнением продукта контентом.

### Причины возникновения

- Команда не успела подготовить достаточное количество рецептов.
- Рецепты плохо структурированы.
- Не хватает простых рецептов для студентов и занятых людей.
- Нет рецептов для популярных наборов продуктов.

### Вероятность

**Высокая**

Для MVP база рецептов, скорее всего, будет небольшой.

### Влияние

**Среднее**

Продукт может работать технически, но пользовательская ценность будет ниже.

### Уровень риска

**Высокий**

### Стратегия реагирования

**Смягчить**

### План реагирования

- Для MVP подготовить минимум 50–100 простых рецептов.
- Сфокусироваться на популярных продуктах: яйца, молоко, хлеб, сыр, картофель, курица, макароны, рис.
- Добавить рецепты на 10–30 минут.
- Разметить каждый рецепт по ингредиентам.
- Добавить в приложение понятное сообщение, если рецептов мало: “Добавьте больше продуктов”.
- Расширять базу рецептов после feedback от пользователей.

### Индикатор риска

Большой процент поисков заканчивается сообщением “Подходящих рецептов пока нет”.

---

## Риск 3. Сложность ввода продуктов пользователем

### Описание

Если пользователю сложно или долго добавлять продукты, он может не дойти до главной ценности — подбора рецептов.

### Тип риска

**Внутренний UX-риск**

Риск связан с пользовательским интерфейсом и удобством приложения.

### Причины возникновения

- Пользователю нужно вручную вводить слишком много продуктов.
- Нет подсказок при вводе.
- Нет популярных быстрых вариантов.
- Интерфейс выглядит перегруженным.
- Неочевидно, что делать после добавления продуктов.

### Вероятность

**Средняя**

На MVP интерфейс может быть простым, но недостаточно удобным.

### Влияние

**Высокое**

Если пользователь не добавит продукты, приложение не сможет подобрать рецепты.

### Уровень риска

**Высокий**

### Стратегия реагирования

**Предотвратить**

### План реагирования

- Добавить подсказки при вводе продукта.
- Добавить список популярных продуктов.
- Сделать кнопку “Подобрать рецепты” заметной.
- Ограничить MVP простым сценарием: добавить продукт → увидеть список → открыть рецепт.
- Провести UX-тестирование на 5–7 пользователях.
- Исправить непонятные элементы интерфейса до релиза MVP.

### Индикатор риска

Пользователи открывают экран “Мой холодильник”, но не добавляют продукты или выходят из приложения.

---

## Риск 4. Scope creep — разрастание функциональности

### Описание

В проект могут начать добавлять слишком много функций: сканирование чеков, распознавание фото холодильника, доставка продуктов, диеты, социальные функции, рекомендации на основе ИИ. Это может сорвать сроки MVP.

### Тип риска

**Внутренний управленческий риск**

Риск связан с управлением объемом работ.

### Причины возникновения

- Команда хочет добавить “еще одну полезную фичу”.
- Нет жестких границ MVP.
- Не используется приоритизация.
- Новые идеи добавляются без оценки трудозатрат.
- Основной сценарий еще не готов, но команда уже делает дополнительные возможности.

### Вероятность

**Высокая**

Для стартап-проекта это очень вероятный риск.

### Влияние

**Высокое**

Разрастание функциональности может привести к срыву сроков и незавершенному MVP.

### Уровень риска

**Критический**

### Стратегия реагирования

**Предотвратить**

### План реагирования

- Зафиксировать MVP-функции:
  - добавление продуктов;
  - подбор рецептов;
  - список недостающих ингредиентов;
  - карточка рецепта.
- Все дополнительные идеи переносить в backlog.
- Использовать приоритизацию MoSCoW.
- Не брать в MVP функции уровня MLP, если не готов основной путь.
- На каждом планировании проверять: “Эта задача нужна для проверки главной гипотезы?”
- Ограничить длительность MVP 4–5 спринтами.

### Индикатор риска

В спринт попадают задачи, которые не относятся к критическому пользовательскому пути.

---

## Риск 5. Проблемы с хранением пользовательских данных

### Описание

Приложение может хранить продукты пользователя, избранные рецепты и информацию о подписке. Ошибки в хранении данных могут привести к потере информации или проблемам с безопасностью.

### Тип риска

**Внутренний технический риск**

Риск связан с базой данных, backend и безопасностью.

### Причины возникновения

- Неправильно спроектирована база данных.
- Нет резервного копирования.
- Ошибки в API.
- Нет базовой защиты данных.
- Ошибка при обновлении приложения может удалить список продуктов.

### Вероятность

**Низкая**

Для MVP объем данных небольшой, но риск нельзя игнорировать.

### Влияние

**Высокое**

Потеря данных может сильно снизить доверие пользователя.

### Уровень риска

**Средний**

### Стратегия реагирования

**Предотвратить**

### План реагирования

- Использовать PostgreSQL.
- Настроить базовые миграции базы данных.
- Добавить валидацию входных данных в API.
- Не хранить лишние персональные данные.
- Настроить резервное копирование базы.
- Ограничить доступ к production-данным.
- Не хранить платежные данные самостоятельно, а использовать платежный сервис.

### Индикатор риска

Пользователи жалуются, что добавленные продукты исчезают или отображаются неверно.

---

## Риск 6. Низкий интерес пользователей после запуска MVP

### Описание

После запуска MVP может оказаться, что пользователи не считают проблему достаточно важной или предпочитают искать рецепты через обычные сайты, YouTube или Telegram-каналы.

### Тип риска

**Внешний рыночный риск**

Риск связан с поведением пользователей и конкуренцией.

### Причины возникновения

- Пользователи не хотят вручную добавлять продукты.
- Существующие альтернативы уже закрывают потребность.
- Ценность приложения недостаточно понятна.
- Пользователь не видит экономии денег или времени.
- Приложение не формирует привычку.

### Вероятность

**Средняя**

Идея понятна, но реальный интерес нужно проверять на пользователях.

### Влияние

**Высокое**

Если пользователям не нужен продукт, дальнейшая разработка не имеет смысла.

### Уровень риска

**Высокий**

### Стратегия реагирования

**Смягчить**

### План реагирования

- Запустить MVP на небольшой группе пользователей.
- Протестировать продукт среди студентов и молодых специалистов.
- Измерять ключевые метрики:
  - количество добавленных продуктов;
  - количество подборов рецептов;
  - открытие карточек рецептов;
  - повторное использование приложения.
- Провести короткие интервью с пользователями.
- Проверить, какая ценность важнее:
  - экономия денег;
  - меньше пищевых отходов;
  - быстрый выбор блюда;
  - рецепты для студентов.
- На основе feedback скорректировать позиционирование продукта.

### Индикатор риска

Пользователи устанавливают приложение, но не возвращаются после первого использования.

# 7. Общая стратегия управления рисками

Для проекта **Recipe from Fridge** используется комбинированная стратегия управления рисками:

1. **Предотвращение** — для критичных рисков, которые могут сорвать MVP.
2. **Смягчение** — для рисков, которые нельзя полностью исключить, но можно уменьшить.
3. **Принятие** — для рисков с низким влиянием.
4. **Передача** — для платежных рисков через использование внешнего платежного сервиса.

Самыми важными рисками являются:

- **Scope creep**, потому что он может сорвать сроки MVP.
- **Низкое качество подбора рецептов**, потому что это главная ценность продукта.
- **Сложность ввода продуктов**, потому что пользователь может не дойти до подбора рецептов.
