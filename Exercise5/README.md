# Практическое задание №5

## Проект

**Recipe from Fridge**

## Краткое описание проекта

**Recipe from Fridge** — это B2C-приложение, которое помогает пользователю подобрать рецепты по продуктам, которые уже есть дома.

Пользователь добавляет продукты из холодильника, а приложение предлагает подходящие рецепты, показывает недостающие ингредиенты и помогает меньше выбрасывать еду.

---

# 1. Hiring Plan

Для MVP проекта нужна небольшая кросс-функциональная команда. Такая команда может самостоятельно пройти путь от идеи до первой рабочей версии продукта: исследовать требования, спроектировать интерфейс, разработать приложение, протестировать его и выпустить MVP.

## Состав виртуальной команды

| Роль | Количество | Главные зоны ответственности |
|---|---:|---|
| Product Manager | 1 | Определяет ценность продукта, приоритизирует фичи, следит за метриками MVP |
| Project Manager / Scrum Master | 1 | Организует процесс разработки, следит за сроками, встречами и блокерами |
| UX/UI Designer | 1 | Проектирует пользовательский путь, делает wireframes и дизайн экранов |
| System Analyst | 1 | Описывает требования, API-контракты, сценарии и бизнес-логику |
| Mobile Developer | 1 | Разрабатывает мобильное приложение на Flutter |
| Backend Developer | 1 | Разрабатывает Backend API, логику подбора рецептов и работу с базой данных |
| QA Engineer | 1 | Тестирует пользовательские сценарии, находит ошибки, проверяет MVP перед релизом |
| DevOps Engineer | 0.5 | Настраивает окружение, деплой, Docker, сервер и базовый мониторинг |

---

## Подробное описание ролей

### 1. Product Manager

**Зоны ответственности:**

- Формирует видение продукта и MVP.
- Определяет, какие функции важны для первой версии.
- Следит за метриками: установки, активные пользователи, просмотренные рецепты, конверсия в подписку.
- Собирает обратную связь от первых пользователей.

**Почему нужен в проекте:**

Product Manager помогает не уйти в разработку лишних функций и сфокусироваться на главной гипотезе: пользователю полезно приложение, которое подбирает рецепты по продуктам из холодильника.

---

### 2. Project Manager / Scrum Master

**Зоны ответственности:**

- Организует работу команды.
- Следит за сроками и прогрессом.
- Проводит планирование, daily, review и ретроспективу.
- Помогает команде устранять блокеры.

**Почему нужен в проекте:**

Даже маленькая команда может терять фокус. Project Manager помогает держать ритм разработки и доводить задачи до результата.

---

### 3. UX/UI Designer

**Зоны ответственности:**

- Проектирует пользовательский путь.
- Создает wireframes и дизайн экранов.
- Делает интерфейс простым и понятным.
- Проверяет, удобно ли пользователю добавлять продукты и выбирать рецепты.

**Почему нужен в проекте:**

Recipe from Fridge — это B2C-приложение. Для обычного пользователя важны простота, понятный интерфейс и быстрый путь к рецепту.

---

### 4. System Analyst

**Зоны ответственности:**

- Описывает функциональные и нефункциональные требования.
- Прорабатывает API-контракты.
- Описывает бизнес-правила подбора рецептов.
- Помогает связать требования, дизайн и backend.

**Почему нужен в проекте:**

Приложение работает с продуктами, рецептами, ингредиентами и совпадениями. Аналитик помогает формализовать эти правила до разработки.

---

### 5. Mobile Developer

**Зоны ответственности:**

- Разрабатывает мобильное приложение.
- Реализует экраны: главный экран, мой холодильник, список рецептов, карточка рецепта.
- Интегрирует мобильное приложение с Backend API.
- Обрабатывает состояния загрузки, ошибок и пустых результатов.

**Почему нужен в проекте:**

Основной пользовательский интерфейс проекта — мобильное приложение.

---

### 6. Backend Developer

**Зоны ответственности:**

- Разрабатывает Backend API.
- Реализует хранение продуктов пользователя.
- Реализует подбор рецептов по ингредиентам.
- Работает с PostgreSQL и базой рецептов.
- Интегрирует API с админ-панелью.

**Почему нужен в проекте:**

Главная логика продукта находится на backend: сравнение продуктов пользователя с рецептами и расчет недостающих ингредиентов.

---

### 7. QA Engineer

**Зоны ответственности:**

- Проверяет основные пользовательские сценарии.
- Тестирует добавление продуктов.
- Тестирует подбор рецептов.
- Проверяет ошибки и пустые состояния.
- Проводит регрессионное тестирование перед релизом.

**Почему нужен в проекте:**

Даже MVP должен работать стабильно. Если пользователь добавил продукты, но не получил рецепты из-за ошибки, ценность продукта не будет проверена.

---

### 8. DevOps Engineer

**Зоны ответственности:**

- Настраивает Docker-окружение.
- Настраивает сервер для backend.
- Помогает с деплоем.
- Настраивает базовый мониторинг.
- Настраивает переменные окружения и безопасность доступа.

**Почему нужен в проекте:**

Для MVP DevOps может быть частичной ролью. На старте не нужен full-time специалист, но нужен человек, который поможет надежно запустить backend.

# 2. Development Framework

## Выбранная методология: Scrum

Для проекта **Recipe from Fridge** выбрана методология **Scrum**.

Scrum подходит для MVP, потому что продукт находится на ранней стадии, требования могут меняться после обратной связи от пользователей, а разработку удобно вести короткими итерациями.

---

## Почему Scrum подходит проекту

### 1. Требования могут меняться

На старте мы не знаем точно, какие функции окажутся самыми важными для пользователей:

- подбор рецептов по продуктам;
- фильтр по времени приготовления;
- напоминания о сроке годности;
- сохранение рецептов;
- список покупок.

После тестирования MVP часть идей может измениться. Scrum позволяет быстро адаптироваться.

---

### 2. MVP удобно делать короткими спринтами

Проект можно разбить на небольшие инкременты:

- спринт 1 — базовые экраны и wireframes;
- спринт 2 — добавление продуктов;
- спринт 3 — подбор рецептов;
- спринт 4 — карточка рецепта и тестирование;
- спринт 5 — сбор обратной связи и улучшения.

Так команда быстрее получает работающий результат.

---

### 3. Нужна постоянная обратная связь

Recipe from Fridge — B2C-продукт. Успех зависит от того, удобно ли пользователю быстро получить рецепт.

Scrum позволяет после каждого спринта показывать результат, получать feedback и менять приоритеты.

---

## Почему не Waterfall

Waterfall хуже подходит проекту, потому что:

- требования могут измениться после первых тестов;
- пользовательская ценность проверяется только на работающем продукте;
- если долго проектировать без проверки, можно сделать ненужные функции;
- MVP требует быстрой проверки гипотезы.

---

## Почему не чистый Kanban

Kanban полезен для поддержки и непрерывного потока задач, но для MVP нам важнее:

- планировать спринты;
- фиксировать цель итерации;
- показывать демо результата;
- регулярно проводить ретроспективы.

Поэтому для первой версии лучше использовать Scrum, а Kanban-доску можно использовать внутри спринта для визуализации задач.

# 3. Team Rituals

Ниже описаны обязательные встречи команды.

## 3.1. Sprint Planning

**Частота:** один раз в 2 недели, в начале спринта.

**Участники:**

- Product Manager;
- Project Manager / Scrum Master;
- UX/UI Designer;
- System Analyst;
- Mobile Developer;
- Backend Developer;
- QA Engineer.

**Цель встречи:**

- выбрать задачи на спринт;
- определить цель спринта;
- уточнить требования;
- оценить задачи;
- договориться, что должно быть готово к концу спринта.

**Пример цели спринта:**

> Реализовать экран “Мой холодильник” и возможность добавления продуктов.

---

## 3.2. Daily Scrum

**Частота:** каждый рабочий день, 10–15 минут.

**Участники:**

- вся команда разработки;
- Project Manager / Scrum Master.

**Цель встречи:**

- понять текущий прогресс;
- выявить блокеры;
- синхронизировать команду;
- не уходить в лишние обсуждения.

**Вопросы на daily:**

1. Что я сделал вчера?
2. Что я планирую сделать сегодня?
3. Есть ли блокеры?

---

## 3.3. Backlog Refinement

**Частота:** один раз в неделю.

**Участники:**

- Product Manager;
- System Analyst;
- UX/UI Designer;
- Mobile Developer;
- Backend Developer;
- QA Engineer.

**Цель встречи:**

- уточнить будущие задачи;
- разбить крупные задачи на маленькие;
- уточнить критерии приемки;
- подготовить задачи для следующего спринта.

**Пример обсуждаемых задач:**

- фильтр рецептов по времени приготовления;
- список недостающих ингредиентов;
- сохранение рецепта в избранное;
- напоминание о сроке годности продукта.

---

## 3.4. Design Review

**Частота:** один раз в неделю или перед началом разработки новой фичи.

**Участники:**

- UX/UI Designer;
- Product Manager;
- System Analyst;
- Mobile Developer;
- Backend Developer.

**Цель встречи:**

- проверить, понятен ли пользовательский сценарий;
- согласовать экраны до разработки;
- выявить проблемы в UX;
- убедиться, что дизайн можно реализовать технически.

**Пример результата встречи:**

> Команда согласовала экран “Подходящие рецепты” и состав данных, которые backend должен отдавать мобильному приложению.

---

## 3.5. Sprint Review

**Частота:** один раз в 2 недели, в конце спринта.

**Участники:**

- вся команда;
- возможные первые пользователи или преподаватель как внешний наблюдатель.

**Цель встречи:**

- показать работающий результат;
- проверить, достигнута ли цель спринта;
- собрать обратную связь;
- понять, что улучшать дальше.

**Пример результата:**

> Команда показывает, как пользователь добавляет яйца, молоко и сыр, после чего получает рецепт омлета.

---

## 3.6. Sprint Retrospective

**Частота:** один раз в 2 недели, после Sprint Review.

**Участники:**

- вся команда.

**Цель встречи:**

- обсудить, что получилось хорошо;
- выявить проблемы в процессе;
- договориться, что улучшить в следующем спринте.

**Пример вопросов:**

1. Что в этом спринте прошло хорошо?
2. Что мешало работе?
3. Что изменим в следующем спринте?

---

## 3.7. Bug Triage

**Частота:** по необходимости, минимум один раз в неделю перед релизом MVP.

**Участники:**

- QA Engineer;
- Product Manager;
- Mobile Developer;
- Backend Developer;
- Project Manager.

**Цель встречи:**

- разобрать найденные баги;
- определить критичность ошибок;
- решить, какие баги исправлять до релиза;
- какие ошибки можно перенести на следующий спринт.

**Примеры критичных багов:**

- пользователь не может добавить продукт;
- рецепты не отображаются;
- приложение падает при открытии карточки рецепта;
- неверно показываются недостающие ингредиенты.

# 4. Рабочий процесс команды

Для работы команды используется Scrum с двухнедельными спринтами.

## Доска задач

Для визуализации задач используется Kanban-доска внутри спринта.

### Колонки доски

| Колонка | Значение |
|---|---|
| Backlog | Все будущие задачи |
| To Do | Задачи, выбранные в текущий спринт |
| In Progress | Задачи в работе |
| Code Review | Задачи на проверке кода |
| Testing | Задачи на тестировании |
| Done | Завершенные задачи |

---

## Правила движения задач

1. Задача не может попасть в `In Progress`, если не описаны требования.
2. Задача не может попасть в `Testing`, если разработчик не завершил реализацию.
3. Задача не может попасть в `Done`, если QA не проверил основной сценарий.
4. Критичные баги исправляются до релиза MVP.
5. Если задача заблокирована, это обсуждается на Daily Scrum.

# 5. Пример плана разработки MVP

## Спринт 1: Проектирование основы

**Цель:** подготовить базовую структуру продукта.

### Задачи

- уточнить MVP;
- подготовить wireframes;
- описать API-контракты;
- подготовить структуру базы данных;
- настроить репозиторий.

### Результат

Команда понимает, какие экраны, API и сущности нужны для первой версии.

---

## Спринт 2: Мой холодильник

**Цель:** реализовать добавление продуктов.

### Задачи

- сделать экран “Мой холодильник”;
- реализовать поле ввода продукта;
- реализовать список продуктов;
- сделать API для добавления продукта;
- протестировать добавление и удаление продуктов.

### Результат

Пользователь может добавить продукты, которые есть дома.

---

## Спринт 3: Подбор рецептов

**Цель:** реализовать главную ценность продукта.

### Задачи

- сделать алгоритм подбора рецептов;
- реализовать API подбора рецептов;
- сделать экран подходящих рецептов;
- показывать недостающие ингредиенты;
- отсортировать рецепты по совпадению.

### Результат

Пользователь получает список рецептов по продуктам из холодильника.

---

## Спринт 4: Карточка рецепта и тестирование

**Цель:** завершить основной пользовательский путь MVP.

### Задачи

- сделать карточку рецепта;
- показать ингредиенты;
- показать шаги приготовления;
- протестировать критический путь;
- исправить критичные баги.

### Результат

Пользователь может пройти полный путь: добавить продукты → получить рецепты → открыть карточку рецепта.

---

## Спринт 5: Feedback и улучшения

**Цель:** собрать обратную связь от первых пользователей.

### Задачи

- показать MVP первым пользователям;
- собрать отзывы;
- проверить, понятен ли интерфейс;
- понять, какие функции нужны дальше;
- обновить backlog.

### Результат

Команда получает данные для следующей итерации продукта.
